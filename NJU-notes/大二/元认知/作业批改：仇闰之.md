# 作业批改：仇闰之
你看虽然你的文档字数不算多，但是在AI的帮助下，我还是给你总结出了这一套东西，分析的字数比原文还要多

> 然后agent试运行了一下, 它识别到我在预习作业中提到了事后复盘、拖延和AI依赖，也指出我没有提供实际调整行为的证据。
>

意不意外

> 这让我看到，有些事情不能只在提示词里说“请不要出错”。如果它必须可靠，就应该尽量变成程序可以检查的约束。
>

这种都是收获，而且是实践中悟出来的道理，比我单纯灌输，印象要深刻多了

## 1. 完成度判定
+ 状态：已完成
+ 依据：完成了从语雀读取文档→调用 DeepSeek 进行单篇分析和纵向比较→生成 Markdown 报告的原型系统。文档详细描述了搭建过程、遇到的两个核心问题及解决方案，并有深刻的元认知反思。虽然系统功能尚不完整（不能自动同步、自动选择比较文档），但作为一个有实际产出和深度反思的作业，判定为已完成。

## 2. 系统需求清单
1. 通过网络爬虫获取语雀中自己写过的文档【基础需求】
2. 调用大模型 API，在程序中内置提示词【基础需求】
3. 让大模型分析自己的"思维链"——后修正为"分析文档中可以观察到的思维过程证据"【亮点：从"分析思维链"到"分析可观察的证据"的需求修正，体现了对 AI 能力边界的清醒认知】
4. 将新文档和历史文档纵向比较，判断自己是否有进步【亮点：纵向对比的动态评价，关注进步而非绝对水平】
5. 区分证据类型：已发生的行动、自我报告、未来意图、概念理解【亮点：精细化的证据分类体系，解决 AI 将自述误认为行动证据的问题】
6. 原文片段编号映射机制（S001/S002→DeepSeek 返回编号→程序映射回原文）【亮点：用程序约束替代提示词约束，解决 AI 悄悄改写原文引用的问题】

## 3. 搭建思路
+ 技术思路：初始四步设想（爬虫获取→调 API→分析思维链→纵向比较）→与 Codex 讨论确定方向，将"分析思维链"修正为"分析可观察的思维过程证据"→Agent 试运行→Codex 检查 DeepSeek 判断是否被原文支持→发现两个问题→逐一用程序化约束解决→生成 Markdown 报告。
+ 所用工具/平台：语雀文档（爬虫获取）、Codex（与 AI 讨论方案+检查 AI 判断）、DeepSeek API（单篇分析+纵向比较）、程序化原文片段编号映射机制。

## 4. 技术评估：方案是否覆盖需求
+ 覆盖情况：核心需求均已覆盖，原型可运行并产出报告。作者诚实标注了三个"还不能"：不能自动同步、不能自动选择最适合比较的文档、不能保证模型对证据的解释永远正确。
+ 逐条对照：
 - 需求1（获取语雀文档）：覆盖
 - 需求2（调 API+内置提示词）：覆盖
 - 需求3（分析思维过程证据）：覆盖，需求已合理修正
 - 需求4（纵向比较判断进步）：覆盖，已实现
 - 需求5（证据类型区分）：覆盖，通过程序实现
 - 需求6（原文片段编号映射）：覆盖，通过程序实现
+ 风险/改进：目前仅有两篇文档可供分析，纵向比较的数据量不足；模型对证据的解释不能保证永远正确；自动同步和自动文档选择未实现。这些风险作者已明确标注。

## 5. 元认知视角评估与鼓励
### 思维过程暴露程度：极高
这是本批次中元认知暴露最充分的文档。核心体现在：

1. **对"完成"标准的自我校准**："如果停在这里，我大概会觉得'API调通了，作业完成了'。但Codex继续检查DeepSeek的判断是否真的被原文支持，问题才一个接一个出现。"——主动质疑了"调通了=完成了"的朴素判断，展现了高水平的自我监控。
2. **对 AI 输出的双层审查**：不仅让 DeepSeek 做分析，还让 Codex 检查 DeepSeek 的判断是否被原文支持——这是对 AI 输出的批判性审查的典型实践，而且形成了 AI→AI 审查的对抗机制。
3. **从提示词约束到程序约束的认知跃迁**："有些事情不能只在提示词里说'请不要出错'。如果它必须可靠，就应该尽量变成程序可以检查的约束。"——这是本次作业中最深刻的元认知洞察之一，将认知层面的教训转化为工程层面的约束设计。
4. **对"证据不足"结论的元认知解读**："这次系统给我的结论是'证据不足'。现在看来，这句话本身就是一个不错的起点。"——将系统的"负面"结论重新解读为有价值的起点，展现了认知重评能力。

### 亮点鼓励
1. **"分析思维链"→"分析可观察的证据"的需求修正**：这是对 AI 能力边界的精准认知——"AI无法知道我没有写出来的真实想法，所以文档里没有出现的内容只能说'未观察到'，不能说我没有思考"。这种区分"未观察到"和"没有"的逻辑严密性非常出色。
2. **程序化约束替代提示词约束**：面对 DeepSeek 悄悄改写原文引用的问题，不是在提示词中反复强调"请不要出错"，而是设计原文片段编号映射机制（S001/S002→编号→映射），用程序约束替代语言约束——"如果它必须可靠，就应该尽量变成程序可以检查的约束"。这是将认知洞察转化为工程实践的典范。
3. **不满足于"调通了"的深度追问**：主动让 Codex 检查 DeepSeek 的判断是否被原文支持，在"看起来能用"的基础上继续追问可靠性，这种不满足于表面的态度是真正的程序性元认知。

### 可提升处
+ 目前仅有两篇文档可供分析，纵向比较的统计意义有限，需要持续积累数据。作者已意识到这一点。
+ 文档未描述技术实现的具体细节（爬虫方式、程序语言、Markdown 报告格式等），如果能补充会更完整。
+ 系统目前是单次运行模式，自动同步和自动文档选择未实现——这些是后续迭代的明确方向。

## 6. 困难总结
+ **认知性**："分析思维链"需求不切实际（AI 无法知道未写出的真实想法）——已解决，修正为"分析可观察的思维过程证据"
+ **技术性/认知性**：DeepSeek 将"我没有调整策略"的自述放入调节能力证据中——已解决，增加证据类型区分（行动/自我报告/未来意图/概念理解）
+ **技术性**：DeepSeek 悄悄改写原文引用（即使提示词要求逐字引用）——已解决，设计原文片段编号映射机制，程序把原文切片编号，AI 只返回编号，程序映射回原文
+ **认知性**：容易满足于"API调通=作业完成"——已克服，通过 Codex 二次审查发现问题
+ **技术性**：不能自动同步、自动选择比较文档——未解决，明确标注为后续方向
+ **认知性**：模型对证据的解释不能保证永远正确——已意识到，未完全解决
+ **数据类**：目前只有两篇文档可供分析——未解决，需持续积累
