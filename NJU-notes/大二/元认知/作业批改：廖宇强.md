# 作业批改：廖宇强
我一直觉得你真的下决心去做一件事之后，投入的精力和取得的成果是正向反馈循环的

但是真正内驱启动的门槛却比较高（要有人踹你一脚的那种）

第三节课，可以讨论一下这个问题

## 1. 完成度判定
+ 状态：已完成
+ 依据：从最初的简单统计脚本迭代到LangChain+tools的Agent原型，最终改用SKILLS方案，系统可运行；文档完整描述了思路演变、代码实现和踩坑过程。

## 2. 系统需求清单
1. 统计语雀知识库文档的文本特征（如前50字出现"第一"的篇数）——源自真实使用场景
2. 通过自然语言描述需求，AI自动生成统计代码并嵌入通用爬虫框架【亮点：将"我看完文档发现好玩的东西→对着agent说→AI生成统计代码"作为核心工作流】
3. 工具链可自由组合应对"看什么"的不同变体
4. 按目录/活动/分组筛选文档范围（而非全库扫描）
5. 自进化能力：agent发现自己缺少某功能时给自己写代码加上（尝试后搁置）
6. 做好看的UI为个人网站做准备（搁置）

## 3. 搭建思路
+ 技术路线演变：① 命令行脚本（requests+BeautifulSoup硬编码）→ ② LangChain + tools Agent原型（细粒度工具+高层工具）→ ③ SKILLS方案
+ 核心设计：将语雀API封装为细粒度工具（list_repos、list_docs、get_doc_plain_text）+ 高层工具（count_docs_keyword_in_prefix），由Agent根据自然语言请求自由组合
+ 工具/平台：语雀API、Python、LangChain、BeautifulSoup、OpenAI兼容模型（DeepSeek等）、SKILLS
+ 设计哲学：prompt结构极简（看哪个知识库+看什么），"塞AI就行了"

## 4. 技术评估：方案是否覆盖需求
| 需求 | 覆盖情况 | 说明 |
| --- | --- | --- |
| 文本特征统计 | ✅ 覆盖 | count_docs_keyword_in_prefix工具实现 |
| 自然语言→代码生成 | ⚠️ 部分覆盖 | LangChain Agent可理解自然语言并调用工具，但并非"生成统计代码嵌入框架"，而是预定义工具组合 |
| 按目录/活动筛选范围 | ✅ 覆盖 | list_docs返回TOC+parent_uuid，SYSTEM_PROMPT强制先缩范围 |
| 防全库扫描 | ✅ 覆盖 | 工具docstring和SYSTEM_PROMPT双重约束doc_ids来源 |
| 自进化能力 | ❌ 搁置 | 识别到难度后主动放弃 |
| UI | ❌ 搁置 | 主动放弃 |

**风险/改进**：

+ 高层工具count_docs_keyword_in_prefix仍是逐篇调用API获取正文，大规模文档时效率瓶颈明显
+ "防止agent偷偷扩展成全库扫描"的约束依赖prompt质量，实际可靠性存疑
+ 最终改用SKILLS但未详细描述实现，文档在此处略显仓促

## 5. 元认知视角评估与鼓励
### 思维过程暴露程度：较高
文档展示了完整的思路演变轨迹：从"一时兴起刷文档→发现特征→写脚本→觉得不够→想加AI→LangChain方案→发现tools设计呆板→改用SKILLS"。每一步转变都有原因说明。

### 亮点鼓励
1. **需求源自真实使用场景**：不是凭空设计需求，而是从"刷xdx文档时发现'第一'高频出现"这个真实观察出发，需求有温度、有个人动机。这种"从真实体验中提取需求"的方式比"想一个需求"更可信。
2. **主动审视工具设计的呆板性**：识别到"目前只是写死了一个提取文档文字特征的tools，假如下次有其他需求，显而易见的不能轻易实现"——这是对系统可扩展性的真实反思，而非满足于"能跑就行"。
3. **对AI输出的批判性审视**：明确记录"cc不但质疑我的url（实际上两个都是对的），还引用错了langchain的api"——不盲信AI输出，保留了具体的AI犯错证据。

### 可提升处
+ 自进化能力的思考停留在"根据我的经验又不太能实现，所以先鸽了"，可以更深入分析为什么难以实现（是技术难度还是需求定义不清），将"鸽了"转化为"下次怎么推进"的计划
+ 多处"鸽了"（自进化、UI），虽然坦诚但可尝试区分"主动放弃"（YAGNI）与"逃避困难"，为后者设一个最小可行尝试
+ SKILLS方案的描述过于简略，缺少与LangChain方案的对比分析（为什么SKILLS更好？解决了什么问题？）

## 6. 困难总结
| 困难 | 类型 | 解决与否 |
| --- | --- | --- |
| book_id和分析工具写死 | 技术性 | ✅ 已解决（LangChain tools + Agent动态选择） |
| AI质疑正确的url、引用错API | 技术性/认知性 | ✅ 已解决（跑起来没大问题，但记录了AI的不可靠） |
| TOC路径更新后agent跑去扫描全部文档 | 技术性 | ✅ 已解决（注意到工具链路上下游需同步维护） |
| tools设计过于呆板，无法应对新需求 | 认知性 | ✅ 已解决（改用SKILLS方案） |
| 自进化agent难以实现 | 技术性 | ❌ 搁置（识别到难度后放弃） |
| 时间不足/觉得小东西不够十小时标准 | 时间精力类 | ⚠️ 部分解决（扩展了方案但仍觉不够） |
| 选择困难（做不做UI、做不做自进化） | 认知性 | ⚠️ 未解决（多处"鸽了"） |
