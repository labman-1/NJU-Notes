# 作业批改：张雨琦
看完你所有的文档，有一种这门课的目标和你个人目标重合的感觉，这很好

想要改变其实是很难的，好在你已经迈出了第一步（没退课不是）

横向看其他同学，固然会发现很多值得学习的内容，奈何认知资源有限

我们需要一个起点，能够从这个点入手，去实践去事上磨

你的课后作业文档，需求分析这部分是以对作业的理解层面展开的

这是我关注的点，虽然内容几乎是一样的，但是潜意识里，如果这是作业（外部要求）而不是因为自己的个人目标而衍生出的需求（内在动机），那么它的后续发展，动力上天然就不足了，也请你想一想这个问题，后续课程一定是强调知行合一的，我们必须要做事，在事上思考反馈，再调整下一步行为，周而复始，这才是认知增长的正确模式

## 1. 完成度判定
+ 状态：已完成
+ 依据：提交了两种完整方案（本地静态网页+定时流水线、Dify工作流），均跑通并展示了数据流与成果截图，附有反思。

## 2. 系统需求清单
1. 让LLM与语雀平台连接，将文档分析结果以直观方式呈现
2. 分析助手常态化更新（定时自动运行）【亮点】
3. 分析维度包含：课程脉络梳理、每课知识点提炼、同学共性总结、针对个人的分析建议【亮点：个性化启发】
4. 网页形态展示，方便查看
5. 快照+增量更新数据机制
6. 第二套方案：Dify workflow 定时触发→拉取语雀增量→单篇LLM分析→综合汇总→邮件发送【亮点：邮件推送闭环】
7. UI审美提升（尝试用设计网站模板、skill给agent学习）

## 3. 搭建思路
+ **方案一**：Python脚本流水线（fetch→clean→analyze→sync→serve），调用语雀v2 API只读拉取，DeepSeek做LLM分析，本地http.server静态网页展示，Windows计划任务每周定时运行。技术栈：Python、语雀官方API、DeepSeek、Claude Code、http.server。
+ **方案二**：Dify工作流，定时触发器→语雀知识库目录获取→增量去重→迭代单篇LLM分析→综合分析→邮件发送。技术栈：Dify、DeepSeek。
+ 两套方案互补：方案一偏工程化、全量重跑；方案二偏流程编排、支持增量。

## 4. 技术评估：方案是否覆盖需求
| 需求 | 覆盖情况 |
| --- | --- |
| LLM连接语雀 | ✅ 两套方案均实现 |
| 常态化更新 | ✅ 方案一用schtasks定时，方案二用Dify定时触发器 |
| 多维度分析 | ✅ 知识点提炼/共性总结/个性化建议三类 |
| 网页展示 | ✅ 方案一有本地网页，方案二输出邮件 |
| 增量更新 | ⚠️ 方案一明确指出"无状态全量重跑"是缺点；方案二有增量去重 |
| UI审美 | ⚠️ 尝试多种方式但自评未显著提升 |

+ **风险/改进**：方案一全量重跑浪费LLM token，应引入内容hash做增量diff；UI审美问题未解决，可考虑用现成前端框架（如Next.js）替代手写静态页。

## 5. 元认知视角评估与鼓励
+ **思维过程暴露程度**：较高。展示了从"直观理解"到"两种方案对比"的完整决策链，包括为什么选方案一（操作方便）、为什么尝试方案二（想学Dify workflow）。
+ **亮点鼓励**：
 1. 做了两套方案而非止步于一套，体现了"穷尽可能"的发散思维，值得鼓励！
 2. 对UI审美不满足于AI默认输出，主动寻找设计模板和skill给agent学习，这种对质量的追求很棒。
 3. 反思中识别出"AI擅长包装成果→产生无瑕错觉"这一深刻认知，这是非常难得的元认知觉察。
+ **可提升处**：反思虽然深刻但偏向事后感慨，若能在开发过程中实时记录"这里我为什么这样做"的中间判断，元认知监控会更加充实。方案一的全量重跑缺点是已知但未采取行动，可以尝试最小增量方案。

## 6. 困难总结
1. **Dify节点间数据衔接频繁出问题**（技术性，已解决——逐个排查）
2. **测试时未先跑通小流程，直接整个文件夹迭代浪费token**（技术性/认知性，已解决——认识到应先小流程测试）
3. **知识库架构复杂、文件命名多样导致归类困难**（技术性，部分解决）
4. **AI生成的UI太丑**（技术性/审美性，未解决——尝试多种方式无显著提升）
5. **"差不多得了"的心态导致被AI的包装迷惑**（认知性，已觉察——通过对比同学作业发现差距）
