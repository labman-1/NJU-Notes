# 作业批改：沈庭宇
请稍稍准备一下，课上可能会邀请你解释你为什么会选择MCP的技术方案（围绕你的需求来阐述）

 然后实践中遇到的新的困难，也可以请你分享一下

## 1. 完成度判定
+ 状态：已完成
+ 依据：系统以MCP Server形态实现，16个只读工具，已在真实课程库（89篇/42位作者）上跑通实测。文档不仅有技术实现，更有三次"被证伪的假设"的深度元认知反思，是本批次中元认知质量最高的作业之一。

## 2. 系统需求清单
1. 为同学的文档写反馈，把"凭印象"换成可以核对的数字【亮点：核心定位精准——不是AI替你写反馈，而是提供可复算的证据】
2. 只读接入，三层边界保障（token只勾读取权限、客户端硬编码只发GET、协议层标readOnlyHint）【亮点：安全边界意识】
3. 将"两篇文档的关系"变成数字（余弦相似度、Jaccard、大纲重合度+语料内百分位）
4. 看批次差集：互评最有价值的是"他写了什么我没写"（coverage_gap）【亮点：从单篇分析上升到批次对比】
5. 问题落到行号（"第42行H2直接跳H4"才是能改的反馈）【亮点：行号级精确定位】
6. 明确不做：不发布、不改写、不打分（前两个越权，打分会把互评变成排名）
7. 课程日历与预习盘点（补充功能）：下次课预习什么、这轮预习大家都写了什么
8. prep_roundup：谁交了谁没交、每人写了什么、全班共识与分歧

## 3. 搭建思路
+ 技术路线：MCP Server形态，16个只读工具
+ 核心设计哲学："工具只取证，判断留给模型"——所有工具输出确定的、可复算的东西（相似度数值、共同词集合、带行号的问题清单），哪些值得说、怎么对同学讲全部交给模型
+ 三种形态对比后选MCP：CLI（一次性、没法追问）vs 本地Web（成本花在无关前端上）vs MCP（互评是对话过程，可追问）
+ 工具/平台：语雀只读API、Python、MCP 2.x、DeepSeek
+ 架构亮点：取数与分析解耦（快照层隔离API和分析层），意外带来"接新数据形态只需插一步派生"的好处

## 5. 元认知视角评估与鼓励
### 思维过程暴露程度：极高
本作业是本批次中元认知质量最高的之一。文档不仅展示了"做了什么"，更系统性地展示了"三次被证伪的假设"——每次都明确写出"我原本以为X，实际发现Y，原因是Z"，这是教科书级的思维过程暴露。

### 亮点鼓励
1. **"三次被证伪的假设"**：这是全文最有价值的部分。第一次（分词只影响可读性→实际毁掉整个相似度体系）、第二次（余弦有通用量纲→绝对值很吃语料）、第三次（使用场景假设完全错误：以为是"我的库vs同学的库"，实际是共享库按作者切分）。每次证伪都不是简单纠错，而是深入分析"为什么这个假设是错的""错误的形态是什么""代价是什么"。特别是第三次，从"一个repo就是一个人"到"真实切分维度是作者"，这是对问题域理解的根本性修正。
2. **"工具只取证，判断留给模型"的设计哲学**：明确阐述了两条理由（防幻觉+措辞跟场景有关），并且发现了一个"当时没想到的好处"——因为没有捷径工具，只能把证据类工具做扎实，pressure传到分析层。这种"设计约束反而倒逼质量"的洞察非常深刻。
3. **"把自己报成没做"的教训**：在盘点功能中发现自己被列入"未见提交"，深入分析字段取错的原因，并提炼出"凡输出会点到具体人名的功能，字段来源必须查证"的原则。特别区分了"结论不够准"和"把做了事的人报成没做"的代价差异——这是对错误严重性分级的元认知。

### 可提升处
+ 三次证伪已经很好，可以进一步提炼为一个通用的"假设检验 checklist"：下次设计系统时，哪些假设需要先用小样本spike验证？
+ O(n³)性能问题已识别但未解决，可补充具体的优化方向（增量计算、缓存中间结果）
+ "取数与分析解耦"的好处是意外发现的，可进一步主动思考"还有哪些设计决策可能有意外收益"
