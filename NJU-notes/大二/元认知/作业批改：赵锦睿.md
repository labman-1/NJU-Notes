# 作业批改：赵锦睿
写的真多...

自己回看自己的文档的感受是什么？

这些技术栈能看懂吗？需要看懂吗？你是怎么考虑的？

## 1. 完成度判定
+ 状态：已完成
+ 依据：项目报告结构完整，L0（文档分析）和L1（检测+写语雀+推送）均已实现并稳定运行，有明确的架构设计、技术栈选型、踩坑记录和未来规划。系统已部署在腾讯云服务器上。

## 2. 系统需求清单
1. 解决企业知识库信息过载（6万+篇文档难以人工阅读）
2. 知识库目录树渲染与层级结构保留
3. 全局搜索（语雀原生search）
4. AI并行分析文档生成结构化摘要（一句话概括/核心要点/值得关注）
5. 文档更新检测（新增/正文变更/标题变更/删除）【亮点：全量快照比对，587篇文档全量监控】
6. 通过Cookie网页接口实现写语雀（建/更新/删除文档、评论、TOC挂载）【亮点：双通道读写分离架构】
7. 指挥Agent通过自然语言指令操作语雀（固定命令集+LLM兜底）
8. 飞书主动推送文档变更摘要
9. Web界面 + CLI命令行双入口
10. 全局API鉴权保护
11. 长期愿景：微信统一入口的个人AI助理（L2规划中）

## 3. 搭建思路
+ 架构设计："双通道读写分离 + LLM抽象层 + 本地缓存"
 - 读通道：语雀开放API（Token v2认证）
 - 写通道：语雀网页内部接口（Cookie认证）
 - LLM层：DeepSeek（可切换Kimi/Claude），抽象隔离
 - 推送：飞书自建应用 + WebSocket长连接（免域名）
 - 部署：腾讯云Ubuntu 24.04 + systemd常驻
+ 核心决策：6万文档按需加载（目录树懒加载+原生搜索兜底+缓存优化，147MB→4KB）
+ 工具/平台：Python 3.12、FastAPI、uvicorn、语雀API（读+网页接口写）、DeepSeek、飞书WebSocket、systemd

**风险/改进**：

+ Cookie认证方式存在过期风险和安全隐患（模拟浏览器操作），长期维护成本较高
+ 全量快照比对在文档量持续增长时性能瓶颈会显现，可考虑增量检测（如webhook）
+ TOC三步挂载是外科手术式操作，虽然加了备份和回滚，但复杂度较高，边际风险存在
+ 未来规划引入SQLite替代文件缓存是正确方向

## 5. 元认知视角评估与鼓励
### 思维过程暴露程度：中等
项目报告以工程文档风格撰写，架构设计和技术决策记录详实，但"为什么这样想"的思维过程相对较少——更多是"做了什么+遇到了什么问题+怎么解决的"，缺少"为什么选这个方案而非另一个"的推理链路。踩坑记录是亮点，展示了真实遇到问题→诊断→解决的过程。

### 亮点鼓励
1. **双通道读写分离架构**：识别到语雀API只读的限制后，没有止步于"只能读"，而是主动探索网页内部接口实现写操作——这种"遇到限制不放弃，找替代路径"的工程思维值得肯定。TOC三步挂载策略更是将复杂问题拆解为可操作的步骤。
2. **6万文档按需加载的架构决策**：从147MB缓存降至4KB，这是对"工程可行性"的真实判断——不是理论上的"可以全量拉取"，而是实际考虑了网络开销、内存占用和响应延迟。这种"在真实约束下做决策"的能力很成熟。
3. **飞书vs企业微信的通道选型对比**：用表格对比域名要求、消息接收方式、部署复杂度，最终选择飞书WebSocket方案绕开备案限制——这是一个完整的"列选项→比优劣→做决策"过程，值得鼓励。

### 可提升处
+ 技术决策的"为什么"可以更深入：例如为什么选DeepSeek而非其他模型？Cookie方案的安全风险如何长期管理？
+ 缺少对自身思维过程的反思：文档更像项目交付报告，较少展示"我在设计时犹豫过什么""我的认知盲区是什么"
+ 未来规划部分（L2微信入口）可以补充"为什么现在不做"的判断依据，体现范围控制意识
