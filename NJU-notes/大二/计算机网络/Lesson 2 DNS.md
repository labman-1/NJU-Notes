DNS即从域名到ip的映射。可以理解为一个key-value的数据库。本质上是一个分布式层次数据库。

Domains are subtrees.
Name is a root-to-leaf path.
RR format：（name, value,type,ttl）
DNS默认传输协议为UDP，默认端口为53.
DDOS攻击：使用大量边缘设备（肉机）向服务器发送大量报文，后来更常见的是向DNS发送大量域名解析请求。
它的核心算法是 **“递归查询 + 迭代查询”**，数据结构是 **“分层树”**。

**工作流程（结合图论/分治思维）**：

当你访问 `www.google.com` 时（你的本地 DNS 解析器发出查询）：

1. **本地缓存**：先查本地 hosts 文件或缓存，没有则走下一步。
    
2. **根服务器（Root DNS）**：本地查询根服务器。根服务器不会告诉你答案，而是告诉你：“去问 `.com` 顶级域服务器”。
    
3. **顶级域服务器（TLD DNS）**：本地查询 `.com` 服务器。它也不会告诉你答案，而是说：“去问 `google.com` 权威服务器”。
    
4. **权威服务器（Authoritative DNS）**：本地查询 Google 的权威服务器，终于拿到 IP 地址（如 142.250.72.14）。
    

**关键概念（考点）**：

- **迭代 vs 递归**：本地 DNS 服务器向根/权威服务器逐步提问是**迭代**；本地主机向本地 DNS 服务器提问是**递归**（本地 DNS 帮你跑完全部流程）。
    
- **传输层协议**：通常使用 **UDP 端口 53**（响应快，适合短查询）。当返回数据过大（如 DNSSEC 加密）时，才会退化为 **TCP 53**。
    
- **缓存机制**：每一层都会缓存查询结果（有 TTL 生存期）。这就是为什么你改了 DNS 记录，全球生效可能需要几分钟到几小时。
    

**与你的算法连接**：这就是一棵**五层的树**（根/顶级/权威/缓存/主机）。从根节点遍历到叶节点，利用你熟练掌握的“分治”策略，把全球 DNS 查询的延迟控制在几十毫秒内。

# FTP 架构：典型的“C/S 架构 + 双连接解耦”

**架构定论**：FTP 属于**客户端/服务器（Client/Server）架构**，但它有一个非常独特的“**控制/数据分离**”设计（这也是它区别于 HTTP 的根本）。

**架构拆解**：

- **控制平面（Control Plane）**：客户端主动连接服务器的 21 端口（TCP），发送 `USER`、`PASS`、`RETR` 等命令。这条连接**全程保持**，直到会话结束。它负责“指挥”。
    
- **数据平面（Data Plane）**：当执行下载/上传命令时，服务器和客户端会**临时新建**一条 TCP 连接（端口 20 或随机高位端口），专门用于传输文件内容。传输完毕，这条连接**立即关闭**。
    

**为什么这么设计？（工程哲学）**  
这其实是把 **“命令通道”** 和 **“大流量数据通道”** 解耦。命令是低频、短小的控制报文，需要稳定；而文件传输是高频、大流量的数据流，需要独立带宽。这在 DLCO 中类似于“指令总线”与“数据总线”分离。

**主动 VS 被动（架构的致命伤）**：

- **主动模式（PORT）**：服务器（20端口）**主动**去连客户端的随机端口。如果客户端有防火墙，连接就会被拦截，导致失败。
    
- **被动模式（PASV）**：服务器告知客户端一个随机端口，客户端**主动**去连接。这是现代 FTP 的默认模式，因为出站连接通常不会被防火墙拦截。
