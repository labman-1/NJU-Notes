### 一、 WWW（万维网）：一个“分布式超文本图”

**本质**：WWW 不是互联网（Internet），而是**建立在互联网之上的一种应用层服务**。它是一张巨大的**“分布式有向图”**，节点是网页（Web Pages），边是超链接（Hyperlinks）。

**工程类比（结合图论）**：
你学过图论，WWW 就是一张**动态更新的图**。每个网页是一个节点，URL 是节点的唯一标识符（像内存地址），HTML 是节点的内容，超链接是指向其他节点的边。搜索引擎（如 Google）的核心算法（PageRank）就是在这张图上做遍历，计算节点的“重要性”。

**关键点**：
- **架构**：经典的 **C/S（客户端/服务器）架构**。客户端是浏览器（User Agent），服务器是 Web Server。
- **资源标识**：用 **URL（统一资源定位符）** 来定位资源（`http://example.com/path/file.html`）。
- **表示语言**：用 **HTML（超文本标记语言）** 描述页面结构。注意，HTML 只是数据的**表现层**，真正的“逻辑”由浏览器解析渲染。

### 二、 HTTP（超文本传输协议）：WWW 的“通信语言”

HTTP 是 WWW 的心脏，它定义了客户端和服务器之间**如何交换报文**。它的设计哲学是**“无状态（Stateless）”**和**“请求-响应（Request-Response）”**。

#### 1. 核心特性（对比之前的协议）
- **无状态**：服务器默认**不记忆**任何之前的请求。每个请求都是独立的（不像 TCP 的连接状态，也不像 FTP 的控制连接）。这就意味着需要引入 **Cookie** 来“伪造”状态（例如购物车）。
- **基于 TCP**：通常运行在 80 端口，依靠 TCP 的可靠传输和流量控制。HTTP/2 之前是文本协议，HTTP/2 之后是二进制帧协议。
- **双连接 vs 单连接**：HTTP **不**像 FTP 那样开两个连接，它**复用同一个 TCP 连接**（HTTP/1.1 的持久连接，HTTP/2 的多路复用），这极大减少了握手开销。

#### 2. 报文结构（考试重点，结合 SICP 的“数据抽象”）
HTTP 报文像一个 **C++ 的 `struct`**，有严格的头部字段：

- **请求报文**：`GET /index.html HTTP/1.1`（方法 + URL + 版本），加上 `Host`、`User-Agent`、`Accept` 等头部。
- **响应报文**：`HTTP/1.1 200 OK`（版本 + 状态码 + 短语），加上 `Content-Length`、`Content-Type` 等头部，空行后跟数据体。

#### 3. 连接演进（结合你的“状态机”和“滑动窗口”知识）
- **HTTP/1.0**：每次请求都建立 TCP 连接，传完就断（效率低，类似非持久）。
- **HTTP/1.1**：**持久连接**，同一 TCP 连接上可以连续发多个请求。但存在**队头阻塞（Head-of-Line Blocking）**，即前面的响应没到，后面的就得等。这就像你在 CPU 流水线里遇到一个长延迟指令，后面的流水线被迫 stall。
- **HTTP/2**：**多路复用**，在一个 TCP 连接上并行发多个请求。这完美解决了队头阻塞问题，相当于你的 CPU 流水线支持了乱序执行（OoO）。
- **HTTP/3**：基于 **UDP**，抛弃了 TCP 的队头阻塞（因为 TCP 的可靠性要求重传），改用 QUIC 协议。

### 三、 Web Infrastructure（Web 基础设施）：支撑 WWW 的“底层引擎”

如果说 WWW 是建筑图纸（HTML/URL），HTTP 是施工语言（协议），那 Web Infrastructure 就是**真正建造这座城市的“混凝土和钢筋”**。它回答了：*“当数十亿人同时访问一个网页时，物理世界中的机器和网络如何协同？”*

从“自顶向下”看，典型的 Web 基础设施是一个多层流水线：

#### 1. 入口层：DNS + 负载均衡器（Load Balancer, LB）
- **DNS**：将域名解析为 IP（你之前学的递归/迭代查询）。
- **LB（如 Nginx / LVS）**：位于服务器集群的最前端，它像一个**流量调度器**。利用你熟悉的**一致性哈希**或**轮询**算法，把请求分发给后端的多个 Web 服务器。
- **为什么需要？**：为了**水平扩展**（加机器）和**高可用**（机器挂了，LB 立即感知并摘除它）。

#### 2. 应用层：Web Server 与 反向代理（Reverse Proxy）
- **Web Server（如 Nginx/Apache）**：负责接收 HTTP 请求，解析静态资源（HTML/CSS/JS），或者把动态请求转发给后端应用（如 FastAPI/Spring）。
- **反向代理（Nginx）**：它站在 Web Server 前面，对外只暴露一个 IP。你可以把它看作一个 **“防火墙门卫”**，负责拦截恶意流量（DDoS 防护）、做缓存、压缩响应体。

#### 3. 数据层：数据库与缓存（Database & Cache）
- **数据库**：如 MySQL/PostgreSQL（你已安装 MySQL），存储用户数据、订单等。
- **缓存（Redis）**：**这是提升性能的核武器**。为什么？因为数据库读取慢（磁盘 I/O），而 Redis 是内存操作（纳秒级）。它就像你 CPU 里的 **L1/L2 Cache**，把最热的数据放在最快的地方。
- **CDN（内容分发网络）**：属于边缘缓存。它不是动数据库，而是把静态资源缓存到离你最近的机房。这利用了**“局部性原理”**，让你在南京访问上海服务器比访问美国服务器快得多。

### 四、 将三者串联（工程级“解剖”）

让我们用你的第一性原理，走一遍完整的流程（想象你在浏览器输入 `www.nju.edu.cn`）：

1.  **DNS 解析**：你的浏览器先向本地 DNS 发起递归查询，最终得到服务器的 IP 地址（例如 1.2.3.4）。
2.  **TCP 握手**：浏览器与 IP 地址建立 TCP 三次握手（你的 ICS 知识）。
3.  **发送 HTTP 请求**：浏览器发送 `GET /index.html HTTP/1.1`。
4.  **到达基础设施**：请求先经过负载均衡器（LB），被分发到一台 Web Server。Web Server 检查缓存（Redis），如果没有，则去 MySQL 查数据，组装成 HTML 返回。
5.  **响应与渲染**：服务器返回 `HTTP/1.1 200 OK` 和 HTML 内容。浏览器接收后，解析 HTML，然后**递归地**发起对 CSS/JS/图片的 HTTP 请求（这些静态资源通常直接命中 CDN，速度极快）。

### 五、 备考与深度思考提示（加缪式的反抗）

**考试常考坑点**：
1.  **HTTP 是无状态的**，为什么能记住用户？——答：通过 **Cookie**（客户端存）和 **Session**（服务端存）。
2.  **HTTP/1.1 的持久连接**解决了什么问题？——答：解决了 TCP 频繁握手带来的 RTT 开销。
3.  **CDN 的工作原理**？——答：利用 DNS 的 **CNAME 别名**，将用户引导到最近的边缘节点。

**思考连接**：
*   你和老师讨论“负载均衡”时，可以提出：*“这本质上是一个动态调度问题，类似于我在操作系统课学过的进程调度，只不过这里调度的对象是 HTTP 请求。”*
*   你可以在本地用 **Docker 搭建一套完整的 Web 基础设施**（Nginx 反向代理 + 两个 Flask 容器 + Redis 缓存），然后用 Wireshark 抓包。你会非常直观地看到：请求如何被 LB 分发，HTTP 头里如何携带 Cookie，以及静态资源如何被 CDN 边缘加速。
