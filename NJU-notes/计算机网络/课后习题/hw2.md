3. **讨论与解释**：
    - TCP 传输层解复用依赖于**四元组**：(源 IP, 源端口号, 目的 IP, 目的端口号)。
        
    - Web 服务器在主机 C 的端口 80 维持一个**监听套接字**，负责等待连接请求。
        
    - 当来自主机 A 和主机 B 的连接请求分别完成 TCP 三次握手后，主机 C 的操作系统内核会分别为它们生成一个全新的**已连接套接字**：
        - 套接字 1：{主机 A 的 IP, 主机 A 的临时端口, 主机 C 的 IP, 80}
        - 套接字 2：{主机 B 的 IP, 主机 B 的临时端口, 主机 C 的 IP, 80}
    - 尽管这两个套接字在主机 C 上的本地端口号完全相同（均为 80），但因为它们的源 IP（或源端口）不同，操作系统内核能够根据到来的报文段的完整四元组，精准地将数据解复用并定向投递到对应的套接字缓冲区。

#### 初始场景
1. **发送方**在状态“等待来自上层的 1”被调用，发送了 **分组 1（seq = 1）**，进入状态“等待 ACK 或 NAK 1”。
2. **接收方**处于状态“等待来自下层的 1”，完好无损地收到了分组 1。
    - 接收方做的事情：提取数据并交付、计算校验和、发出 **ACK**。
    - **接收方状态转移**：转移到了右边的 **“等待来自下层的 0”** 状态
        
#### 差错发生
1. 接收方发出的这个 **ACK** 在信道回传途中**发生了比特翻转**。
    
2. **发送方**收到了这个损坏的响应报文：

    - 发送方规则（图 3-11）：收到损坏报文（无法辨识是 ACK 还是 NAK），发送方只能保守地**重传当前分组**，即**重新发送分组 1**
        
    - 发送方状态：**依然停留在“等待 ACK 或 NAK 1”**。
        
#### 致命的逻辑死锁
1. **接收方**收到了重传的分组 1：
    
    - 此时接收方身处 **“等待来自下层的 0”** 状态。
    - **观察图 3-60 左边状态的自环条件**：  
        rdt_rcv(rcvpkt) && (corrupt(rcvpkt) || has_seq1(rcvpkt))
        
    - 接收方发现收到了分组 1，它认为这是一个“期望之外的错误分组”。
        
    - **看看图 3-60 执行了什么动作**：  
        make_pkt(sndpkt, NAK, chksum)
它向发送方发送了一个 NAK
        
2. **发送方**收到这个合法的 NAK：
    
    - 发送方在“等待 ACK 或 NAK 1”状态下收到 NAK，按照规则：**再次重传分组 1！**
        
3. **接收方**再次收到分组 1：
    
    - 接收方依然在“等待来自下层的 0”，再次触发自环，**再次发送 NAK！**
        

#### 结论

**系统陷入死锁**：

- 发送方在等待：**“针对分组 1 的 ACK”**（以便推进到 0）；
    
- 接收方在等待：**“发送方发来分组 0”**（否则我就永远回 NAK）。
    
- 双方都在等待对方做出自己期望的动作，通信彻底瘫痪，无限循环重传分组 1 和 NAK。
# P14
假定发送方只是**偶尔发送数据**。只用 NAK 的协议（记为协议1）会比使用 ACK 的协议（记为协议2）更差。考虑接收方反馈丢失的情景：协议1下发送方由于没收到NAK，认为已成功送达，继续发送下一个包，之前的错误无法弥补；协议2下发送方未受到ACK，触发重传，然后接收方收到了和刚才重复的包，再次发送ACK，这个过程是可靠的。
假设发送方要**发送大量数据，且端到端连接很少丢包**，则用 NAK 的协议（记为协议1）会比使用 ACK 的协议（记为协议2）更好。理由如下：
- **逆向信道开销骤降（“没有消息就是好消息”）**：
    - ACK 协议每发一个（或每两个）数据包就必须生成一个反向确认包。如果发送$10^7$个包，就要产生数百万个 ACK，严重侵占反向链路带宽与主机 CPU 中断。
    - NAK 协议在正常传输时**完全保持静默**。如果丢包率仅为$10^{-6}$，整个过程中只有几十个 NAK 被发出，反向带宽开销几乎降为 0。
    - 同时，由于数据流是源源不断、紧密连续发送的，只要中间丢了任何一个包，下一个包会在几毫秒内立即到达并冲刷出“序号空洞”，触发 NAK 重传，时延惩罚极小。
# P18

### 一、 协议核心设计原则与数学不变式

1. **窗口大小**：
   * 发送方和接收方的窗口大小均固定为 **$N = 2$**。
2. **序号空间大小**：
   * 根据选择重传（SR）协议的不变式 $W_{\text{sender}} + W_{\text{receiver}} \le \text{序号空间大小}$，这里 $2 + 2 = 4$。
   * 因此只需 **4 个全局序号**：$\{0, 1, 2, 3\}$（占用 2 个比特）。
   * **Pair 0** 由分组 `0` 和 `1` 组成；
   * **Pair 1** 由分组 `2` 和 `3` 组成；
   * 随后模 4 回绕（$\{0, 1\} \to \{2, 3\} \to \{0, 1\} \dots$）。
   * *(注：由于信道保证不损坏且不乱序，4 个序号足以杜绝新老分组混淆)*。

---

### 二、 报文格式

1. **数据报文（发送方 $\to$ 接收方）**：
   * `seqnum`（2 bits）：分组序号，取值为 $0, 1, 2, 3$。
   * `data`（可变长）：上层应用交付的有效载荷。
   * *(说明：因题设信道“不会损坏”，无需 Checksum 字段)*。

2. **确认报文（接收方 $\to$ 发送方）**：
   * `acknum`（2 bits）：被确认分组的序号，取值为 $0, 1, 2, 3$。

---

### 三、 过程调用接口定义

* `start_timer(i)` / `stop_timer(i)`：针对特定序号 $i$ 的独立定时器控制。
* `udt_send(packet)`：将报文交付给不可靠底层信道。
* `rdt_rcv(packet)`：从物理信道接收到达的报文。
* `deliver_data(data)`：向上层应用按序交付数据。

---

### 四、 有限状态机（FSM）详细描述

#### 1. 发送方（Sender）FSM
发送方维护状态变量：
* `base` $\in \{0, 2\}$：表示当前正在发送的Pair的起始序号。
* `ack_received[4]`：布尔数组，记录当前对的两个分组是否已获确认。

```text
[状态 1：等待上层调用第 base 对数据]
  事件：上层交付两个数据块 (data_a, data_b)
  动作：
    pkt_0 = make_pkt(base, data_a);
    pkt_1 = make_pkt(base + 1, data_b);
    udt_send(pkt_0);
    udt_send(pkt_1);
    start_timer(base);
    start_timer(base + 1);
    ack_received[base] = false;
    ack_received[base + 1] = false;
    转移到 -> [状态 2：等待第 base 对的 ACK]

[状态 2：等待第 base 对的 ACK]
  事件 1：rdt_rcv(rcvpkt) (收到 ACK 分组，序号为 a)
  动作：
    if (a == base || a == base + 1) {
        stop_timer(a);
        ack_received[a] = true;
        if (ack_received[base] && ack_received[base + 1]) {
            base = (base + 2) % 4; // 推进到下一对
            转移到 -> [状态 1：等待上层调用第 base 对数据]
        }
    }
    // 若收到过期的旧 ACK，直接忽略

  事件 2：timeout(i) (序号为 i 的分组定时器超时，i 为 base 或 base + 1)
  动作：
    udt_send(pkt_i);     // 仅重传未确认的那一个（SR 特性）
    start_timer(i);      // 重启该报文的定时器
```

---

#### 2. 接收方FSM
接收方维护状态变量：
* `rcv_base` $\in \{0, 2\}$：期待接收的当前“对”的起始序号。
* `rcv_buf[4]`：缓存接收到的有效数据。
* `has_received[4]`：标记当前对中的各个分组是否已到达。

```text
[初始状态：等待来自下层的报文] (rcv_base = 0)
  事件：rdt_rcv(rcvpkt) (收到数据报文，序号为 s)
  动作：
    // 1. 凡收到报文，必单独回送对应的 ACK
    make_pkt(ackpkt, s);
    udt_send(ackpkt);

    // 2. 判断是否落在当前接收窗口 [rcv_base, rcv_base + 1] 内
    if (s == rcv_base || s == rcv_base + 1) {
        rcv_buf[s] = extract_data(rcvpkt);
        has_received[s] = true;

        // 若这一对的两个分组均已收齐，按序交付并推进窗口
        if (has_received[rcv_base] && has_received[rcv_base + 1]) {
            deliver_data(rcv_buf[rcv_base]);
            deliver_data(rcv_buf[rcv_base + 1]);
            has_received[rcv_base] = false;
            has_received[rcv_base + 1] = false;
            rcv_base = (rcv_base + 2) % 4; // 推进期待窗口
        }
    }
    // 3. 若落在前一对 [ (rcv_base - 2 + 4)%4, ... ]，上方第 1 步已重发 ACK，此处不做数据处理
```

# P22
a.发送方窗口内可能包含的分组序号范围是\[k-4,k+3\]。
* **引理**：
  1. 接收方期待 $k$，意味着接收方已经**按序接收并累计确认了直到 $k-1$ 为止的所有分组**。
  2. 接收方不会凭空期待 $k$；因此发送方此前必然已经至少发送过分组 $k-1$。
  3. 信道严格按序传输（不发生重排序），发送窗口大小为 $N = 4$。

* **极值边界推导**：
  * **下界场景（ACK 传输最大延迟 / 全滞留在途中）**：
    * 接收方成功接收了 $k-4, k-3, k-2, k-1$，并把下一个期待值更新为 $k$。
    * 但接收方发出的关于这些分组的 ACK **全部还在物理信道上传播，尚未到达发送方**。
    * 此时发送方收到的最新 ACK 还是 $k-5$，因此发送方的窗口基序号（`send_base`）仍然停留在 **$k-4$**。
    * 此时发送方的窗口区间为：$[k-4, k-1]$。
    * **窗口包含的最小序号为 $k-4$**。
  * **上界场景（ACK 瞬时到达，发送方顶格发送）**：
    * 接收方发出的所有直到 $k-1$ 的 ACK **已经全部被发送方完好接收**。
    * 发送方的窗口基准向前滑动到了 `send_base = k`。
    * 只要发送缓冲区有数据，发送方可以把当前窗口内允许发送的全部 4 个分组 $[k, k+1, k+2, k+3]$ 倾囊发出。
    * 此时发送方的窗口区间为：$[k, k+3]$。
    * **窗口包含的最大序号为 $k+3$**。

* **结论**：
  发送方的当前窗口区间必然是形如 $[m, m+3]$ 的长度为 4 的窗口，其中 $k-4 \le m \le k$。因此，发送方窗口内可能出现的分组序号的并集恰好为 **$[k-4, k+3]$**（运算均在模 1024 空间下进行）。
b.正在从接收方飞向发送方的所有可能 ACK 分组中，ACK 字段的值可能有{k-4,k-3,k-2,k-1}.下界：假设ACK（k-5）在路上，则发送方未收到ACK（k-5），其窗口至多为\[k-5,k-2\]，不可能发送k-1给接收方，而接收方期待k，矛盾。故下界至少为k-4，经检验，ACK（k-4）可以在路上。上界：由于接收方期待k，显然上界为k-1.
