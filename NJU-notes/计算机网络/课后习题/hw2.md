    - TCP 传输层解复用依赖于**四元组**：(源 IP, 源端口号, 目的 IP, 目的端口号)。

        - 套接字 1：{主机 A 的 IP, 主机 A 的临时端口, 主机 C 的 IP, 80}
        - 套接字 2：{主机 B 的 IP, 主机 B 的临时端口, 主机 C 的 IP, 80}
    - 尽管这两个套接字在主机 C 上的本地端口号完全相同（均为 80），但因为它们的源 IP（或源端口）不同，操作系统内核能够根据到来的报文段的完整四元组，精准地将数据解复用并定向投递到对应的套接字缓冲区。

#### 初始场景
1. **发送方**在状态“等待来自上层的 1”被调用，发送了 **分组 1（seq = 1）**，进入状态“等待 ACK 或 NAK 1”。
2. **接收方**处于状态“等待来自下层的 1”，完好无损地收到了分组 1。
    - 接收方做的事情：提取数据并交付、计算校验和、发出 **ACK**。
    - **接收方状态转移**：转移到了右边的 **“等待来自下层的 0”** 状态
        
#### 差错发生
1. 接收方发出的这个 **ACK** 在信道回传途中**发生了比特翻转**。
    
2. **发送方**收到了这个损坏的响应报文：

    - 发送方规则（图 3-11）：收到损坏报文（无法辨识是 ACK 还是 NAK），发送方只能保守地**重传当前分组**，即**重新发送分组 1**
        
    - 发送方状态：**依然停留在“等待 ACK 或 NAK 1”**。
        
#### 致命的逻辑死锁
1. **接收方**收到了重传的分组 1：
    
    - 此时接收方身处 **“等待来自下层的 0”** 状态。
    - **观察图 3-60 左边状态的自环条件**：  
        rdt_rcv(rcvpkt) && (corrupt(rcvpkt) || has_seq1(rcvpkt))
        
    - 接收方发现收到了分组 1，它认为这是一个“期望之外的错误分组”。
        
    - **看看图 3-60 执行了什么动作**：  
        make_pkt(sndpkt, NAK, chksum)
它向发送方发送了一个 NAK
        
2. **发送方**收到这个合法的 NAK：
    
    - 发送方在“等待 ACK 或 NAK 1”状态下收到 NAK，按照规则：**再次重传分组 1！**
        
3. **接收方**再次收到分组 1：
    
    - 接收方依然在“等待来自下层的 0”，再次触发自环，**再次发送 NAK！**
        

#### 结论

**系统陷入死锁**：

- 发送方在等待：**“针对分组 1 的 ACK”**（以便推进到 0）；
    
- 接收方在等待：**“发送方发来分组 0”**（否则我就永远回 NAK）。
    
- 双方都在等待对方做出自己期望的动作，通信彻底瘫痪，无限循环重传分组 1 和 NAK。
# P14
假定发送方只是**偶尔发送数据**。只用 NAK 的协议（记为协议1）会比使用 ACK 的协议（记为协议2）更差。考虑接收方反馈丢失的情景：协议1下发送方由于没收到NAK，认为已成功送达，继续发送下一个包，之前的错误无法弥补；协议2下发送方未受到ACK，触发重传，然后接收方收到了和刚才重复的包，再次发送ACK，这个过程是可靠的。
假设发送方要**发送大量数据，且端到端连接很少丢包**，则用 NAK 的协议（记为协议1）会比使用 ACK 的协议（记为协议2）更好。理由如下：
- **逆向信道开销骤降（“没有消息就是好消息”）**：
    - ACK 协议每发一个（或每两个）数据包就必须生成一个反向确认包。如果发送$10^7$个包，就要产生数百万个 ACK，严重侵占反向链路带宽与主机 CPU 中断。
    - NAK 协议在正常传输时**完全保持静默**。如果丢包率仅为$10^{-6}$，整个过程中只有几十个 NAK 被发出，反向带宽开销几乎降为 0。
    - 同时，由于数据流是源源不断、紧密连续发送的，只要中间丢了任何一个包，下一个包会在几毫秒内立即到达并冲刷出“序号空洞”，触发 NAK 重传，时延惩罚极小。
# P18

### 一、 协议核心设计原则与数学不变式

1. **窗口大小**：
   * 发送方和接收方的窗口大小均固定为 **$N = 2$**。
2. **序号空间大小**：
   * 根据选择重传（SR）协议的不变式 $W_{\text{sender}} + W_{\text{receiver}} \le \text{序号空间大小}$，这里 $2 + 2 = 4$。
   * 因此只需 **4 个全局序号**：$\{0, 1, 2, 3\}$（占用 2 个比特）。
   * **Pair 0** 由分组 `0` 和 `1` 组成；
   * **Pair 1** 由分组 `2` 和 `3` 组成；
   * 随后模 4 回绕（$\{0, 1\} \to \{2, 3\} \to \{0, 1\} \dots$）。
   * *(注：由于信道保证不损坏且不乱序，4 个序号足以杜绝新老分组混淆)*。

---

### 二、 报文格式

1. **数据报文（发送方 $\to$ 接收方）**：
   * `seqnum`（2 bits）：分组序号，取值为 $0, 1, 2, 3$。
   * `data`（可变长）：上层应用交付的有效载荷。
   * *(说明：因题设信道“不会损坏”，无需 Checksum 字段)*。

2. **确认报文（接收方 $\to$ 发送方）**：
   * `acknum`（2 bits）：被确认分组的序号，取值为 $0, 1, 2, 3$。

---

### 三、 过程调用接口定义

* `start_timer(i)` / `stop_timer(i)`：针对特定序号 $i$ 的独立定时器控制。
* `udt_send(packet)`：将报文交付给不可靠底层信道。
* `rdt_rcv(packet)`：从物理信道接收到达的报文。
* `deliver_data(data)`：向上层应用按序交付数据。

### 四、 有限状态机（FSM）详细描述

#### 1. 发送方（Sender）FSM
发送方维护状态变量：
* `base` $\in \{0, 2\}$：表示当前正在发送的Pair的起始序号。
* `ack_received[4]`：布尔数组，记录当前对的两个分组是否已获确认。

```text
[状态 1：等待上层调用第 base 对数据]
  事件：上层交付两个数据块 (data_a, data_b)
  动作：
    pkt_0 = make_pkt(base, data_a);
    pkt_1 = make_pkt(base + 1, data_b);
    udt_send(pkt_0);
    udt_send(pkt_1);
    start_timer(base);
    start_timer(base + 1);
    ack_received[base] = false;
    ack_received[base + 1] = false;
    转移到 -> [状态 2：等待第 base 对的 ACK]

[状态 2：等待第 base 对的 ACK]
  事件 1：rdt_rcv(rcvpkt) (收到 ACK 分组，序号为 a)
  动作：
    if (a == base || a == base + 1) {
        stop_timer(a);
        ack_received[a] = true;
        if (ack_received[base] && ack_received[base + 1]) {
            base = (base + 2) % 4; // 推进到下一对
            转移到 -> [状态 1：等待上层调用第 base 对数据]
        }
    }
    // 若收到过期的旧 ACK，直接忽略

  事件 2：timeout(i) (序号为 i 的分组定时器超时，i 为 base 或 base + 1)
  动作：
    udt_send(pkt_i);     // 仅重传未确认的那一个（SR 特性）
    start_timer(i);      // 重启该报文的定时器
```

---

#### 2. 接收方FSM
接收方维护状态变量：
* `rcv_base` $\in \{0, 2\}$：期待接收的当前“对”的起始序号。
* `rcv_buf[4]`：缓存接收到的有效数据。
* `has_received[4]`：标记当前对中的各个分组是否已到达。

```text
[初始状态：等待来自下层的报文] (rcv_base = 0)
  事件：rdt_rcv(rcvpkt) (收到数据报文，序号为 s)
  动作：
    // 1. 凡收到报文，必单独回送对应的 ACK
    make_pkt(ackpkt, s);
    udt_send(ackpkt);

    // 2. 判断是否落在当前接收窗口 [rcv_base, rcv_base + 1] 内
    if (s == rcv_base || s == rcv_base + 1) {
        rcv_buf[s] = extract_data(rcvpkt);
        has_received[s] = true;

        // 若这一对的两个分组均已收齐，按序交付并推进窗口
        if (has_received[rcv_base] && has_received[rcv_base + 1]) {
            deliver_data(rcv_buf[rcv_base]);
            deliver_data(rcv_buf[rcv_base + 1]);
            has_received[rcv_base] = false;
            has_received[rcv_base + 1] = false;
            rcv_base = (rcv_base + 2) % 4; // 推进期待窗口
        }
    }
    // 3. 若落在前一对 [ (rcv_base - 2 + 4)%4, ... ]，上方第 1 步已重发 ACK，此处不做数据处理
```

# P19

#### 1. 报文格式
* **数据报文（A $\to$ 广播）**：
  * `seq`：1 比特（0 或 1）。
  * `data`：上层有效载荷。
  * `checksum`：差错检测码。
* **确认报文（B/C $\to$ A）**：
  * `acknum`：1 比特（0 或 1）。
  * `source_id`：标识符（字符 `'B'` 或 `'C'`）。
  * `checksum`：差错检测码。

#### 2. 发送方 A 的 FSM 设计
A 在每个周期需要维护**两个布尔标志位**：`b_acked` 和 `c_acked`。
我们以**“发送序号 0 的周期”**为例（序号 1 结构完全对称）：

```text
               [等待来自上层的 0]
                      |
                      | 1. rdt_send(data)
                      | ------------------------------------
                      | pkt = make_pkt(0, data, chksum)
                      | udt_send(pkt)
                      | start_timer()
                      | b_acked = false; c_acked = false;
                      v
             [等待来自 B 和 C 的 ACK 0]
                      |
        +-------------+-------------+
        |                           |
        | 2. rdt_rcv(ackpkt) &&     | 3. timeout()
        |    notcorrupt(ackpkt) &&  | -----------------
        |    ackpkt.acknum == 0     | udt_send(pkt)
        | -----------------------   | start_timer()
        | if (ackpkt.src == 'B')    |
        |     b_acked = true;       |
        | if (ackpkt.src == 'C')    |
        |     c_acked = true;       |
        | if (b_acked && c_acked)   |
        |     stop_timer();         |
        |     进入 [等待上层 1] 状态 |
```

#### 3. 接收方（以 C 为例，B 完全相同）的 FSM 设计
接收方 C 的行为本质上就是标准的 **rdt2.2 接收方**，只需在回送 ACK 时打上自己的标签 `'C'`：
* **状态：等待来自下层的 0**：
  * **收到正确的 seq 0**：提取数据交付上层，发回报文 `make_pkt('C', 0, chksum)`，转移到**“等待来自下层的 1”**。
  * **收到损坏包 或 seq 1（重复旧包）**：重发上一轮的确认 `make_pkt('C', 1, chksum)`，**状态保持不变**。

# P20

#### 2. 报文格式
* A 与 C 之间的信道：数据包 `pkt(seq, data, chksum)`，ACK `ack(acknum, chksum)`。
* B 与 C 之间的信道：格式相同。
* 序号只需 **0 和 1**（各自独立的模 2 空间）。

#### 3. 实体 A 与 B 的设计
A 和 B **各自完全退化为标准的 rdt3.0 发送方**
* A 拥有自己的序号状态（0 $\to$ 1 $\to$ 0）和定时器。
* B 同样拥有自己的序号状态和定时器。
* 它们彼此不知道对方的存在，只需忠实地“发包 $\to$ 等 ACK $\to$ 超时重传”。

#### 4. 实体 C 的交替状态机（核心控制枢纽）
C 的状态机是一个**四状态环（严格保证 A 和 B 的交替）**：
1. `Wait_A_0`：等待 A 发送 seq 0。
2. `Wait_B_0`：等待 B 发送 seq 0。
3. `Wait_A_1`：等待 A 发送 seq 1。
4. `Wait_B_1`：等待 B 发送 seq 1。

以状态 **`Wait_A_0`** 为例解析状态机的处理规则：
* **事件 1：收到来自 A 的无差错且 seq=0 分组**：
  * 动作：`deliver_data(pkt.data)`（向上层交付 A 的数据）；发送 `make_pkt(ACK, 0)` 给 A。
  * 状态转移：**流转到 `Wait_B_0`**（轮到 B 了）。
* **事件 2：收到来自 A 的损坏包 或 seq=1（重传旧包）**：
  * 动作：向 A 重发针对 A 的上一个确认（即 `ACK 1`）；状态不转移。
* **事件 3：在此时收到了来自 B 的任何分组**：
  * **关键处理**：因为此时还没有收到 A 的数据，C 不能向上交付 B 的数据。
  * **极简优雅策略**：直接**丢弃该分组，不向 B 发送任何确认**
  * **系统自愈过程**：B 因为收不到 ACK 会在本地触发超时重传；与此同时 C 耐心等待 A；一旦 A 完成交付，C 切入 `Wait_B_0`，此时 B 刚好重传过来，握手立即命中

# P22
a.发送方窗口内可能包含的分组序号范围是\[k-4,k+3\]。
* **引理**：
  1. 接收方期待 $k$，意味着接收方已经**按序接收并累计确认了直到 $k-1$ 为止的所有分组**。
  2. 接收方不会凭空期待 $k$；因此发送方此前必然已经至少发送过分组 $k-1$。
  3. 信道严格按序传输（不发生重排序），发送窗口大小为 $N = 4$。

* **极值边界推导**：
  * **下界场景（ACK 传输最大延迟 / 全滞留在途中）**：
    * 接收方成功接收了 $k-4, k-3, k-2, k-1$，并把下一个期待值更新为 $k$。
    * 但接收方发出的关于这些分组的 ACK **全部还在物理信道上传播，尚未到达发送方**。
    * 此时发送方收到的最新 ACK 还是 $k-5$，因此发送方的窗口基序号（`send_base`）仍然停留在 **$k-4$**。
    * 此时发送方的窗口区间为：$[k-4, k-1]$。
    * **窗口包含的最小序号为 $k-4$**。
  * **上界场景（ACK 瞬时到达，发送方顶格发送）**：
    * 接收方发出的所有直到 $k-1$ 的 ACK **已经全部被发送方完好接收**。
    * 发送方的窗口基准向前滑动到了 `send_base = k`。
    * 只要发送缓冲区有数据，发送方可以把当前窗口内允许发送的全部 4 个分组 $[k, k+1, k+2, k+3]$ 倾囊发出。
    * 此时发送方的窗口区间为：$[k, k+3]$。
    * **窗口包含的最大序号为 $k+3$**。

* **结论**：
  发送方的当前窗口区间必然是形如 $[m, m+3]$ 的长度为 4 的窗口，其中 $k-4 \le m \le k$。因此，发送方窗口内可能出现的分组序号的并集恰好为 **$[k-4, k+3]$**（运算均在模 1024 空间下进行）。
b.正在从接收方飞向发送方的所有可能 ACK 分组中，ACK 字段的值可能有{k-4,k-3,k-2,k-1}.下界：假设ACK（k-5）在路上，则发送方未收到ACK（k-5），其窗口至多为\[k-5,k-2\]，不可能发送k-1给接收方，而接收方期待k，矛盾。故下界至少为k-4，经检验，ACK（k-4）可以在路上。上界：由于接收方期待k，显然上界为k-1.

# P32

#### a. 4 个样本的平滑往返时延表达式
根据平滑往返时延递推公式：
$$\text{平滑值} = (1 - \alpha) \cdot \text{上一轮平滑值} + \alpha \cdot \text{新样本}$$
其中 $\alpha = 0.1$。设初始基准从第 4 个样本开始，向前递推：
$$\text{第3步} = 0.1 \times \text{样本}_3 + 0.9 \times \text{样本}_4$$
$$\text{第2步} = 0.1 \times \text{样本}_2 + 0.9 \times (0.1 \times \text{样本}_3 + 0.9 \times \text{样本}_4)$$
$$\text{第1步} = 0.1 \times \text{样本}_1 + 0.9 \times [0.1 \times \text{样本}_2 + 0.09 \times \text{样本}_3 + 0.81 \times \text{样本}_4]$$
展开后得到：
$$\text{平滑值} = 0.1 \times \text{样本}_1 + 0.09 \times \text{样本}_2 + 0.081 \times \text{样本}_3 + 0.729 \times \text{样本}_4$$

#### b. 推广到 $n$ 个样本的一般公式
$$\text{平滑值} = \sum_{j=1}^{n-1} \alpha (1 - \alpha)^{j-1} \text{样本}_j + (1 - \alpha)^{n-1} \text{样本}_n$$

#### c. 指数移动平均的原因
随着样本与当前时刻距离的增加（即下标 $j$ 增大），赋予该历史样本的权重系数按照 $(1 - \alpha)^{j-1}$ 的形式呈几何级数（指数形式）衰减。较新的样本拥有较大的权重，越久远的样本权重衰减越快，因此该算法被称为指数移动平均。

# P36

#### 收到 3 个冗余确认才执行快速重传的原因
底层物理网络并不保证分组传输的绝对按序到达，可能会由于多路径转发或路由器调度引起轻微的数据报重新排序。
若数据发生轻微失序，接收方会立即产生 1 个或 2 个冗余确认。如果协议在收到第 1 个冗余确认时就立刻重传，会导致大量因单纯乱序而引发的不必要重传，严重浪费网络带宽。
要求连续收到 3 个冗余确认作为门限，能够以极大概率确认该分组已在网络中丢失，而非仅仅经历短时失序，从而在快速恢复与误判代价之间取得了最佳工程平衡。

#### 结论
加性增加性减算法不能收敛于平等共享。

#### 论证
考虑两条连接共享瓶颈带宽时的吞吐量二维平面图。
* 纵轴和横轴分别代表连接 1 和连接 2 的吞吐量。
* 理想平等共享线为从原点出发的 45 度射线（$x_1 = x_2$）。
* 满载线为 $x_1 + x_2 = R$。
1. **加性增阶段**：当总带宽未饱和时，两条连接的窗口各自增加一个单位，轨迹沿斜率为 1 的方向（平行于 45 度线）向右上移动。
2. **加性减阶段**：当出现丢包时，若采用加性减，两条连接各自减去固定的常量，其轨迹沿斜率为 1 的方向向左下平移。
由于增加向量和减少向量均平行于 45 度线，两条连接的吞吐量之差在整个动态调整过程中保持恒定，系统仅在同一条直线上来回振荡，永远无法改变最初的不公平比例，因此不会收敛于平等共享。

  根据简化模型，C1 的调整周期为 50 毫秒，C2 为 100 毫秒。每次发生丢包后，两端窗口减半。
  在经历初始剧烈下调后，系统进入周期性震荡循环。由于 C1 调整窗口的频率是 C2 的两倍（每 100 毫秒内 C1 增长 2 次而 C2 仅增长 1 次），窗口在极小值与恢复之间交替。
  经过 1000 毫秒（包含多个震荡周期）的持续削减与增加后，根据离散状态跟踪表，在第 1000 毫秒结束时，两者的拥塞窗口均回落处于低谷状态，各为 1 个报文段（或震荡初期的 2 个报文段）。

#### b. 长时间运行能否取得相同带宽
* **结论**：不能。
* **原因**：C1 拥有更短的往返时延，其窗口调整与增长频率是 C2 的两倍。在加性增阶段，C1 增长速度更快；在乘性减恢复阶段，C1 也能更快重新拉升发送速率。因此，较短往返时延的连接将不公平地抢占绝大部分链路带宽。

# P54

#### 1. 丢包率 $L$ 与最大拥塞窗口 $W$ 的函数关系
设当前窗口大小为 $w$。在一个往返时间内，发送方发出 $w$ 个报文段并收到 $w$ 个确认。
每个确认使窗口增加 $a$，则在一个往返时间内窗口增加量为：
$$\Delta w = a \cdot w$$
即下一轮窗口大小为：
$$w_{\text{next}} = (1 + a)w$$
窗口呈指数增长。
设窗口从 $W/2$ 增长到 $W$ 所需的往返时间轮数为 $k$：
$$\frac{W}{2} (1 + a)^k = W \implies (1 + a)^k = 2 \implies k = \frac{\ln 2}{\ln(1 + a)}$$
在一个拥塞周期内发送的分组总数 $N$ 为等比数列求和：
$$N = \sum_{i=0}^{k} \frac{W}{2} (1 + a)^i = \frac{W}{2} \cdot \frac{(1 + a)^{k+1} - 1}{a}$$
将 $(1 + a)^k = 2$ 代入：
$$N = \frac{W}{2} \cdot \frac{2(1 + a) - 1}{a} = \frac{W(1 + 2a)}{2a} \approx \frac{W}{2a}$$
由于在一个周期末尾只丢失一个报文段，丢包率 $L$ 为：
$$L = \frac{1}{N} = \frac{2a}{W(1 + 2a)} \approx \frac{2a}{W}$$
即最大拥塞窗口与丢包率成反比：$W \approx \frac{2a}{L}$。

#### 2. 增长耗时恒定的论证
从 $W/2$ 增加到 $W$ 所需的时间为：
$$\text{时间} = k \cdot \text{往返时延} = \frac{\ln 2}{\ln(1 + a)} \cdot \text{往返时延}$$
由于 $a$ 是固定正数，该式中的轮数 $k$ 是一个与最大窗口 $W$ 无关的常数。因此，无论连接的吞吐量多高、最大窗口 $W$ 多大，窗口翻倍所需的时间始终恒定。

# P55

#### 1. 10 Gbps 速率下容忍丢包率的推导
根据教材给出的宏观吞吐量公式：
$$\text{平均吞吐量} \approx \frac{1.22 \times \text{报文段大小}}{\text{往返时延} \times \sqrt{L}}$$
已知报文段大小为 1500 字节（即 12000 比特），往返时延为 100 毫秒（即 0.1 秒）。
代入吞吐量 10 Gbps（即 $10 \times 10^9 \text{ bps}$）：
$$10 \times 10^9 = \frac{1.22 \times 12\,000}{0.1 \times \sqrt{L}} = \frac{146\,400}{\sqrt{L}}$$
$$\sqrt{L} = \frac{146\,400}{10 \times 10^9} = 1.464 \times 10^{-5}$$
求平方得：
$$L = (1.464 \times 10^{-5})^2 \approx 2.14 \times 10^{-10} \approx 2 \times 10^{-10}$$
对应的丢包间隔为每 $1 / (2 \times 10^{-10}) = 50$ 亿个分组才允许出现一次丢包。

#### 2. 100 Gbps 连接所能容忍的丢包率
将吞吐量设为 100 Gbps（即 $100 \times 10^9 \text{ bps}$）：
$$100 \times 10^9 = \frac{146\,400}{\sqrt{L}}$$
$$\sqrt{L} = \frac{146\,400}{100 \times 10^9} = 1.464 \times 10^{-6}$$
求平方得：
$$L = (1.464 \times 10^{-6})^2 \approx 2.14 \times 10^{-12} \approx 2 \times 10^{-12}$$
即在 100 Gbps 链路下，所能容忍的丢包率下降至约 $2 \times 10^{-12}$（相当于每发送 5000 亿个报文段仅能丢失一个）。
